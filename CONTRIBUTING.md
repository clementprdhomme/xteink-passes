# Contributing to Passes

Thanks for helping. Passes is a small app for the Xteink X4 Pro and X4 Classic e-readers, written in Lua for the XTApp platform.

## Reporting a problem or an idea

Open an issue and pick the form that fits: a bug, a code that doesn't scan, a feature request, or a translation. Never paste the data of a real ticket or card, or a photo where its code can be read: it may be enough to use it.

## Changing the code

1. Read [Development](#development) below: it explains how the app is built and the rules to follow.
2. Install [luacheck](https://github.com/lunarmodules/luacheck) and turn on the pre-commit hook, as explained in [Linting](#linting).
3. Test the change in the [Studio](https://xtapp-ai.xteink.cc/studio) preview with both the X4 Pro and the X4 Classic profiles: one has touch, the other only keys.
4. Open a pull request and go through its checklist.

## Translations

The messages are in `lang/`, one `<locale>.tsv` file per language. `lang/en.tsv` is the reference: its comments explain where each message is shown and how long it can be. The app already covers every language the device offers, except Traditional Chinese, which shows Simplified Chinese since the device's font lacks some Traditional characters, and Arabic, which shows English since the device can't draw right-to-left text.

To fix a translation, change the message in `lang/<locale>.tsv`, keep each `{name}` as it is, and check that the text still fits on the screen.

## Development

The app is written in Lua 5.5 for the [XTApp](https://xtapp-ai.xteink.cc) platform (API 2.12). Test it in the [Studio](https://xtapp-ai.xteink.cc/studio) preview with both the X4 Pro and X4 Classic profiles: one has touch, the other only keys.

```
src/             scripts and manifest.json
  index.lua      entry point: loads the modules and switches screens
  lockscreen.lua lock-screen script: draws the chosen pass while the device is locked
  class_*.lua    base classes: Screen and Control
  screen_*.lua   one file per screen
  control_*.lua  one file per control (button, icon button, form row, ticket…)
  lib_*.lua      barcode encoders (Aztec, Code 128, ITF, PDF417)
  utils*.lua     helpers: text sizes, storage, lock screen, dialogs and code generation
  constants.lua  layout values, formats, and the app version shown on the About screen
assets/          images (.png packaged in the app, .ase LibreSprite sources)
lang/            messages: en.tsv (the reference, with notes for translators) and one <locale>.tsv per language
docs/            README screenshots and store artwork (not part of the app)
.luacheckrc      linter settings: line length and the globals the app defines
.githooks/       pre-commit hook that runs the linter
.github/         lint workflow, Dependabot settings, issue forms and pull request template
```

- Screens draw their content in `draw_content` and declare their controls in `create_controls`. The base `Screen` draws the controls, keeps the focus and dispatches input to them.
- Every control is a `ui:button` of the XTApp UI library. On touch devices no key event reaches the library, so no focus is drawn.
- Passes are saved as JSON in the app's private storage (`passes.json`). The id of the pass on the lock screen is in `ctx.state`, which the lock-screen session reads; it draws the pass with `PassScreen:draw_content`, without the buttons.
- QR codes are generated by the device's built-in encoder. The other formats use the encoders in `src/lib_*.lua`.
- The pass screen draws a ticket with a stub holding the name and notes: below square codes (QR, Aztec), beside long ones (Code 128, ITF, PDF417), which are turned a quarter to run down the ticket. The code's data is written under it. Beside a long code, the stub and the data are turned too: they're drawn into off-screen layers and drawn back with `rotate`, which needs the `image_transform` capability (required in the manifest). The sizes in `src/constants.lua` (`PASS.TICKET_*`, `PASS.STUB_SIZE`) must match the `ticket-pass` and `ticket-pass-vert` images.
- In dark mode the device inverts the whole screen. `PassScreen:draw_content` reads `ctx.device:display().dark` on every draw and then draws the code, its data and a block around them inverted, so the device shows them black on white for scanners. A code that can't be drawn leaves its message to follow dark mode.
- The app can't read its own manifest, so `APP.VERSION` in `src/constants.lua` must match `version` in `src/manifest.json`. When a feature, a control or a third-party file changes, update the About text (`about.*` in `lang/en.tsv`, laid out in `AboutScreen:get_content`) too.
- Every text the user sees is a message in `lang/en.tsv`, read with `ctx.i18n:t`; a key missing from a language falls back to English. When a message changes, update it in every `lang/<locale>.tsv`. Dialogs and short messages have byte limits (noted in `en.tsv`): a longer text isn't shown, so open them with `utils["dialog"]`, which cuts the texts to fit.
- The small system font has no Chinese, Japanese or Korean characters: a text that has some is drawn in the medium font, taller. Size text boxes with `utils["text"].get_line_height(font, text)` (or `get_max_line_height(font)` for a text not known yet), not `font.line_height`.

### Linting

The code is checked with [luacheck](https://github.com/lunarmodules/luacheck), set up in `.luacheckrc`:

- Lines are at most 120 characters long, comments included.
- Only the globals listed in `.luacheckrc` are allowed. A new class or a new constant table has to be added there; anything else belongs in a `utils[...]` module or a local.
- Luacheck doesn't support Lua 5.5 yet, so it checks the code as Lua 5.4. Keep to the syntax the two share.

Install it with LuaRocks (`luarocks install luacheck`), then run it from the root of the repository:

```sh
luacheck src
```

The pre-commit hook in `.githooks/` runs it on the staged Lua files and stops the commit if it reports anything. Turn it on once per clone:

```sh
git config core.hooksPath .githooks
```

The `Lint` workflow in `.github/workflows/` runs it on GitHub for every push and pull request.

## Releasing

### Before releasing

- Check that `luacheck src` reports nothing and that the `Lint` workflow passes on GitHub.
- Test in the Studio preview with both the X4 Pro and the X4 Classic profiles, in the "Real device" display mode, then on a device: create, edit, move and delete passes, every format, the long-press menu, the front light, the lock screen, dark mode and the About screen.
- Try a few languages, such as German (long words) and Japanese or Chinese (taller text). On the device, the language comes from the system settings.
- Check that the README and its screenshots (`docs/screenshots/`), the store cover (`docs/store/cover.png`, which shows screenshots too), this file, the About texts (`about.*` in `lang/en.tsv`) and every `lang/<locale>.tsv` describe the app as it is.

### 1. Update the manifest

- Set the new version (`major.minor.patch`: patch for fixes, minor for new features, major for changes that break something) in `version` in `src/manifest.json` and in `APP.VERSION` in `src/constants.lua`. The app can't read its manifest, and the About screen shows `APP.VERSION`.
- If the code uses a newer API, raise `api` and update the API version in the "Install" section of the README and in [Development](#development). Add any new capability the code needs to `requires`.
- Never change `app_id` once the app is published: a different `app_id` is a different app, and an update would not keep the user's passes.
- If the format of the saved passes (`passes.json`) changed, raise `STORAGE.VERSION` in `src/constants.lua` and convert the previous format when it's loaded, so users keep their passes after the update.

### 2. Publish on XTEINK Studio

Submit the app from [XTEINK Studio](https://xtapp-ai.xteink.cc/studio), with the store icon (`docs/store/icon.png`, 512 × 512) and the store cover (`docs/store/cover.png`, 1200 × 675). The package expects `manifest.json` and the scripts at its root, with `assets/` and `lang/` next to them:

- every file in `src/`, at the root;
- the `.png` files of `assets/`, in `assets/` (the `.ase` files are LibreSprite sources, not part of the app);
- `lang/`, as it is.

On the first submission, the store issues the app's final `app_id` (`u-` followed by 8 hexadecimal digits) and writes it into the Studio project. Copy it into `src/manifest.json` before the next step, so the release on GitHub and later releases have it and update the same app.

### 3. Create a release on GitHub

Commit and push the changes (with the `app_id` of a first submission), then create the release and its tag (`v` followed by the version) from `main`, with notes that say what changed for users:

```bash
gh release create v1.0.0 --target main --title "1.0.0" --notes "What changed for users"
```
